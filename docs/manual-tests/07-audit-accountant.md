# Manual Test Guide: Audit Log (Accountant Role)

**Document ID:** `07-audit-accountant`  
**Page Name:** Audit Log (`/audit`)  
**Target User Role:** Accountant (`accounts`)  
**Verification Target:** Activity Log inspection, Date/Table/Action/User filters, JSON Details expandable inspector, Deleted Items muster list, and strict MD-only restriction on the Restore operation (`restore_record` RPC).

---

## 1. Page Overview

- **Purpose:** Centralized, immutable security and compliance ledger tracking every critical data creation, inline edit, field correction, soft-deletion, and restoration across all modules (Expenses, Payments, Contractor Bills, Attendance, Purchase Orders, Receipts, Cash Closings, and Client Receipts).
- **Menu Path:** Click **Audit Log** in the left sidebar navigation menu, or navigate directly to `http://localhost:5173/audit` (or hosted domain equivalent).
- **Login Used:** User account assigned the `accounts` role in `user_roles`.
- **Route Guard:** Guarded by `<RequirePermission permission="canViewAuditLog" label="Audit Log">`. Because the `accounts` role has `canViewAuditLog = true`, the page loads completely for the Accountant.
- **Critical Role Boundary (Restore Operation):**
  - While the Accountant has full read and filter access across the **Activity Log** and the **Deleted Items** tab, clicking the **"Restore"** button calls the database RPC `restore_record`.
  - The database RPC `restore_record` strictly enforces `SELECT public.is_md() INTO v_is_md;`.
  - When an Accountant attempts to click **Restore**, the backend operation fails with the toast error:
    *"Permission denied. Only Managing Director (MD) can restore records."*

### Action 7: Verify Backend Block on Restore Operation
- **Location:** Tab **Deleted items** → Button **"Restore"** on any row.
- **Preconditions:** User is logged in as **Accountant** (`accounts` role).
- **Steps:**
  1. On the first deleted item in the list, locate the green button **"Restore"**.
  2. Click **Restore**.
  3. Button momentarily displays state: *"Restoring…"*.
  4. The request calls Supabase RPC `restore_record` with the table name and record ID.
- **Expected Result (Backend Role Enforcement):**
  - Database function `restore_record` checks `is_md()`. Because the user has the `accounts` role, the check returns `false`.
  - Toast error notification appears:
    *"Permission denied. Only Managing Director (MD) can restore records."*
  - The record is **not** restored.
  - The row remains listed on the Deleted Items tab.

## 6. Permission Tests

Execute these tests to confirm role boundaries for the `accounts` role.

### Test PERM-AUD-01: Accountant Read Access Verification
1. Log in as **Accountant** (`accounts` role).
2. Navigate to `/audit`.
3. **Verify:**
   - Page loads without permission locks.
   - Accountant can inspect all audit logs across all business modules.
   - Database policy `audit read` permits accounts:
     ```sql
     CREATE POLICY "audit read" ON public.audit_logs

     ```

## 9. Open Questions, UNVERIFIED Items & Observations

1. **Audit Log Access vs. Restore Rights:**
   - In `src/lib/permissions.ts`, `canViewAuditLog` is `true` for `accounts`.
   - In `supabase/migrations/20260921000000_audit_trail_system.sql`, the RLS policy `audit read` allows:
     ```sql
     USING (public.has_role(auth.uid(), 'md') OR public.has_role(auth.uid(), 'accounts'));
     ```
   - However, in `supabase/migrations/20261026000000_security_and_approval_fixes.sql` line 116–131, the `restore_record` RPC strictly allows only MD:
     ```sql
     SELECT public.is_md() INTO v_is_md;
     IF NOT COALESCE(v_is_md, false) THEN
       RAISE EXCEPTION 'Permission denied. Only Managing Director (MD) can restore records.';
     END IF;
     ```
   - **Conclusion:** The Accountant has full visibility into who modified or deleted records, but the decision to **un-delete / restore** a record is reserved exclusively for the Managing Director. This is verified and fully functional.
